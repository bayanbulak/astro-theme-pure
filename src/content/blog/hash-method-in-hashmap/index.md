## 一、源码原文（JDK 1.8）

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 :
        (h = key.hashCode()) ^ (h >>> 16);
}
```

这一行做了 3 件事：
1. 拿到 key 的原始 hashCode（int，32 位）
2. 把它无符号右移 16 位（高 16 位移到低 16 位，原高位补 0）
3. 与原值做异或（XOR）

## 二、为什么要这么做？—— "扰动函数"

核心目的：让 hashCode 的高 16 位也参与到桶下标的计算，降低哈希冲突。

关键背景：
- HashMap 计算桶下标用的是 (n - 1) & hash
- 数组初始容量 n = 16，(n-1) = 15 = 0000...0000 1111
- 这个 & 运算只有最低 4 位有效，其余 28 位全部被丢弃！

如果直接用 key.hashCode()，那么:
- 高 28 位的信息完全没用
- 只要两个 key 的 hashCode 低 4 位相同就会冲突
- 即使 hashCode 分布很均匀，桶下标也会分布很差

## 三、举个例子

假设两个 key 的 hashCode 是：
```
key1.hashCode() = 0xABCD0001
                = 1010 1011 1100 1101  0000 0000 0000 0001

key2.hashCode() = 0x12340001
                = 0001 0010 0011 0100  0000 0000 0000 0001
```

直接 & 15（n=16）：
```
key1: ...0001 & 1111 = 0001  →  桶 1
key2: ...0001 & 1111 = 0001  →  桶 1   冲突！
```

加上扰动后 (h ^ (h >>> 16))：
```
key1: 0xABCD0001 ^ 0x0000ABCD = 0xABCDABCC
      末 4 位: 1100 → 桶 12

key2: 0x12340001 ^ 0x00001234 = 0x12341235
      末 4 位: 0101 → 桶 5

不冲突 ✓
```

## 四、为什么是右移 16 位？而不是 8、4？

因为 int 是 32 位，右移 16 位刚好让高 16 位与低 16 位"对齐"做异或，保证：
- 原本被丢弃的高位信息全部混入低位
- 一次运算就够了，性能损耗最小（JDK 1.7 做了 4 次扰动，1.8 简化为 1 次）

## 五、为什么用 XOR 而不是 +、&、|？

- & (与)：结果偏向 0，分布不均
- | (或)：结果偏向 1，分布不均
- \+ (加)：会有进位丢失信息
- ^ (异或)：0/1 分布均匀，可逆，不会丢失信息 —— 是混合 bit 的最佳运算

## 六、一句话总结

"hash() 方法叫做扰动函数，把 hashCode 的高 16 位异或到低 16 位，让高位也参与桶下标的运算。因为 HashMap 初始容量只有 16，(n-1) & hash 只能用到 hashCode 的低 4 位，高位信息会被浪费。这样做能在 hashCode 分布不够散列时，降低冲突概率。"

## 七、加分追问

Q: JDK 1.7 和 1.8 的 hash() 有什么区别？
> A: 1.7 做了 4 次位移 + 5 次异或，扰动更复杂；1.8 简化为 1 次位移 + 1 次异或，因为引入了红黑树兜底，即使冲突多了性能也不会退化太严重，所以选了更轻量的实现。

Q: 为什么不直接 hash % n？
> A: 当 n 是 2 的幂时，(n-1) & hash 等价于 hash % n，但位运算比取模快得多（CPU 一个周期 vs 几十个周期）。这也是为什么 HashMap 容量必须是 2 的幂。
